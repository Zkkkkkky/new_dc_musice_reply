# 15首 FamiStudio 曲目扩容改造执行计划

状态：执行中（G0-G5 已实现并通过双模拟器 15 曲矩阵；G6 等待绑定表，G7 的长时场景压力测试待继续）
制定日期：2026-09-17  
目标ROM：`dist/roms/新DC上.nes`、`dist/roms/新DC下.nes`  
扩容参考：`DC_kuorong.nes`

## 1. 目标和边界

本次改造需要同时满足以下目标：

1. 两个目标ROM的扩容方式与 `DC_kuorong.nes` 保持一致：Mapper 194、1MB PRG、256KB CHR、扩容后的固定Bank位于 `$7E/$7F`。
2. 保留原游戏音乐与音效引擎；新增音乐走独立的 FamiStudio 引擎，形成“原引擎＋FamiStudio引擎”的双引擎结构。
3. 不采用参考ROM中的三首示例曲目，改为 `assets/music/01 精修通用驱动（F000-F100-F160）/` 下的15首精修NSF。
4. 支持 FCEUX 2.6.6 与 Mesen；两者都必须能够冷启动、进入游戏、触发全部新曲并持续运行。
5. 所有构建必须可重复，原始ROM与NSF不得被原地修改。
6. 原ROM的PRG `$00-$3F` 原则上必须逐字节保持不变；新增代码、数据、跳板和补丁优先放入扩容空间，不以“看似空白”为理由占用原Bank。
7. 必须保留与现有修改器协作的工作流，不能只保证扩容ROM单独运行。

默认不把实体MMC3卡带或烧录卡兼容性列为本轮交付门槛。标准实体MMC3通常只有512KB PRG寻址能力，如需实体硬件支持，应另立硬件Mapper方案。

## 2. 已确认事实

- 15个NSF均为单曲、NTSC、2A03文件，加载/初始化/播放入口分别为 `$F000/$F100/$F160`。
- 15个NSF的首个4KB驱动页完全相同；不同部分为歌曲数据，因此只需要一套公共引擎。
- NSF内部使用 `$5FF8-$5FFF` 的4KB虚拟换页，不能把NSF整文件直接复制进Mapper 194 ROM运行。
- 14首歌曲的有效数据范围不超过8KB。
- `It's Not Anime - zz高达精修.nsf` 的有效数据范围约为10345字节，需要跨越 `$8000-$9FFF` 与 `$A000-$AFFF` 两段地址。
- FCEUX 2.6.6实测能够正确访问 Mapper 194 的 `$60/$64` 等高Bank；本项目不设计 `$60→$20` 一类低Bank镜像兼容层。

## 3. 原ROM保护与修改器兼容原则

### 3.1 不可变区域

除iNES Header中扩容所必需的PRG容量字段外，默认保护规则如下：

1. 输入ROM的原PRG `$00-$3F` 在输出ROM中必须逐字节一致。
2. 原固定Bank `$3E/$3F` 不直接打补丁；先复制到扩容后的 `$7E/$7F`，只修改运行时使用的新副本。
3. 原音频Bank不直接打补丁；复制到 `$60` 后，只修改 `$60` 副本。
4. 原CHR内容不被改写；扩容ROM中的活动CHR必须由当前输入ROM的CHR重新复制生成。
5. 新增歌曲、引擎、桥接器、映射表和状态数据全部位于扩容Bank或经审计确认的新增RAM区域。

构建器必须自动比较输出ROM的原PRG区域与输入ROM；出现任何未列入白名单的差异时直接失败。白名单默认为空，不因构建方便而自动扩大。

### 3.2 为什么“保留原地址”仍不足以保证旧修改器兼容

扩容后，文件中会出现多个原数据副本：

- 原CHR在旧文件偏移处成为PRG `$40-$5F` 的影子副本，真正活动CHR移动到1MB PRG之后。
- 原固定Bank `$3E/$3F` 仍保留，但运行时固定窗口使用的是 `$7E/$7F` 副本。
- 原音频Bank仍保留，但双引擎入口可能运行在 `$60` 副本。

如果旧修改器使用硬编码文件偏移，它可能只修改旧副本，导致修改在运行时不可见。因此不能仅凭“修改器成功保存文件”判定兼容。

### 3.3 默认安全工作流

默认采用以下顺序：

```text
原尺寸ROM
   ↓ 现有修改器
修改后的原尺寸ROM
   ↓ 本项目扩容构建器
1MB PRG双引擎ROM
```

每次用户重新使用旧修改器后，都以修改器输出的原尺寸ROM重新运行扩容构建器。构建器从最新输入重新复制CHR、固定Bank和音频Bank，再重新应用扩容区补丁，从而避免副本失配。

在完成旧修改器写入范围审计以前，不承诺旧修改器可以直接打开并安全保存最终1.25MiB扩容ROM。

### 3.4 原空间修改例外

如果某个最终事件绑定无法通过扩容区桥接器、运行时上下文判定或固定Bank副本完成，必须先提供：

1. 必须修改原空间的技术原因；
2. 精确文件偏移、PRG Bank、CPU地址、原值和新值；
3. 对现有修改器的影响分析；
4. 可回滚补丁及验证结果；
5. 用户对该例外的明确确认。

未满足以上条件，不修改原PRG或原CHR。

## 4. 已冻结的 Bank 布局

静态审计和运行时验证后，实际布局冻结如下；与早期候选相比，曲目数据从 `$65` 开始，以保留 `$60` 音频副本和 `$64` 桥接容器。

| Bank | 计划用途 |
| --- | --- |
| `$00-$3F` | 保留目标ROM原512KB PRG，要求逐字节一致 |
| `$40-$5F` | 按参考ROM扩容方式保留原CHR影子区 |
| `$60` | 原音乐Bank副本、音频入口及必要跳板 |
| `$61-$63` | 旧三曲测试区清空 |
| `$64` | 双引擎桥接代码容器 |
| `$65-$73` | 15首精修曲目的主数据，每首一个8KB Bank |
| `$74` | 重定位后的公共驱动及包装器 |
| `$75` | 公共驱动及超长曲目的第三个4KB数据页 |
| `$76` | Bank切换跳板 |
| `$77` | 迁移后的56个原版音效数据 |
| `$78-$7D` | 预留扩展空间 |
| `$7E-$7F` | 原 `$3E/$3F` 固定Bank副本及固定区钩子 |

候选CPU窗口：

- R6：歌曲主数据，映射至 `$8000-$9FFF`。
- R7：桥接器、歌曲尾部和FamiStudio引擎，映射至 `$A000-$BFFF`。
- 公共引擎地址：`$B000-$BCFF`；包装器从 `$BD00` 开始。
- 桥接器位于 Bank `$64` 的 CPU `$B500`。
- 运行时分发器位于 Bank `$76` 的 CPU `$8000`。

尺寸、歌曲指针、RAM占用、嵌套 NMI 与两个模拟器的 Bank 映射均已通过自动化验证。

### 阶段3：重建公共FamiStudio引擎

任务：

1. 根据NSF公共驱动实际启用的功能，使用对应版本的FamiStudio引擎源码重新编译，而不是二进制硬搬 `$F000` 驱动。

3. 用MMC3 R6/R7替代NSF `$5FF8-$5FFF` 虚拟换页。
4. 审计目标游戏的零页、内部RAM和WRAM占用，为FamiStudio状态分配无冲突区域。
5. 对引擎代码尺寸设置硬性上限，防止越过 `$BFFF`。
6. 先用一首最小曲目和 `It's Not Anime` 建立短曲/长曲双样本原型。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 超长曲目超过单个8KB窗口 | 无法沿用三曲方案的一曲一Bank布局 | 使用R6主Bank＋R7尾部/引擎专用Bank，先完成长曲原型 |
| FamiStudio RAM与游戏冲突 | 随机死机、事件或存档损坏 | 运行时追踪RAM占用，冻结无冲突内存图后再集成 |
| 新音乐指令与原命令冲突 | 错曲、错误音效或控制命令失效 | 静态扫描＋运行时命令覆盖统计，禁止仅凭空白字节判断 |
| NMI中切Bank未恢复 | 图形、事件或主程序跑飞 | 使用Mapper影子状态，所有出口统一恢复，并做连续切曲压力测试 |
| 两个目标ROM地址不同 | 一个版本正常、另一个版本损坏 | 公共实现＋独立ROM配置，不直接复制绝对补丁地址 |
| NSF音色或功能配置不一致 | 移植后声音变化 | 以共同驱动页为配置依据，比较APU轨迹和完整循环 |
| FCEUX与Mesen行为差异 | 单一模拟器通过但交付不稳定 | 每个阶段门都要求双模拟器验证，不在末期才补测 |
| 旧修改器只更新原文件偏移 | CHR、固定Bank或音频修改未同步到运行时副本 | 默认使用“先修改、后扩容”；构建时从最新输入重建全部副本 |
| 为绑定音乐直接改原事件区 | 后续修改器保存时覆盖绑定或产生未知冲突 | 优先使用扩容区上下文桥接；任何原空间例外需逐项确认 |

## 7. 需要用户确认的内容决策

技术工作可以先按15个顺序测试ID推进；最终事件绑定前，需要确认每首曲目对应的人物、战斗或剧情场景。该映射属于内容设计，不由工具自动推断。

如果用户要求旧修改器直接编辑最终扩容ROM，还需要提供修改器文件或准确版本，以便单独审计其文件大小判断、Header解析和写入偏移；在此之前采用“先修改、后扩容”工作流。

## 8. 完成定义

只有同时满足以下条件，任务才算完成：

1. 两个目标ROM均按参考方式扩容到1MB PRG。
2. 原游戏功能、原音乐和原音效没有阻断级回归。
3. 15首精修曲目全部可触发、可持续播放、可停止、可切换并正确循环。
4. FCEUX 2.6.6与Mesen均通过静态、场景、循环和压力测试。
5. 构建脚本、曲目映射、验证证据、交付ROM和哈希清单齐全且可重复生成。
6. 原PRG `$00-$3F` 除获批例外外与本次输入ROM逐字节一致，并通过自动化保护区检查。
7. 已提供并验证修改器兼容工作流，不会把“能保存扩容ROM”误判为“修改实际生效”。
